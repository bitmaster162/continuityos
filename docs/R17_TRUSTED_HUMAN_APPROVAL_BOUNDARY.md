# R17 Trusted Human Approval Boundary

R17 adds the authenticated Human approval boundary immediately after R16:

`PLAN -> CODE -> TEST -> REVIEW -> HUMAN_MERGE_GATE_REQUEST -> TRUSTED_HUMAN_APPROVAL`

It converts a current R16 Human-gate request into exact merge eligibility only after verifying an Ed25519 Human approval envelope.

## Security contract

The signed approval binds all of the following:

- repository
- R16 request receipt ID
- work-order ID and generation
- policy version
- baseline commit
- candidate commit and candidate tree
- parity mode
- expected and observed delta digests
- explicit approval of an intentional delta when required
- signer ID and key ID
- issuance time, expiry and approval nonce

The public key is selected from an externally supplied key registry whose canonical SHA-256 digest must exactly match a trusted operator-side pin.

Private signing keys are never accepted, loaded, stored or generated by this module.
## Freshness and replay

Before accepting approval, R17 re-runs the R16 current-request validator against the current repository/base/head/tree. Approval TTL is bounded to 15 minutes with a 60-second future-clock tolerance.

Approval consumption is delegated to a `consume_once(approval_id)` replay-guard contract. The included `InMemoryApprovalReplayGuard` is atomic within one process. R18 supplies the durable one-host SQLite equivalent, and R19 supplies the explicit production binding that always constructs it from an operator-provided absolute file path with no in-memory fallback.

## Merge eligibility

A successful approval creates a `MERGE_ELIGIBLE` receipt with `can_merge=true`, but it does not execute a merge. The receipt embeds the exact R16 request and signed Human envelope.

Final handoff must call `require_merge_eligibility_current`, which revalidates:

- receipt integrity
- current repository/base/head/tree
- the embedded R16 Human-gate request
- registry pin and Ed25519 signature
- TTL and clock policy
- signed candidate/parity/delta bindings
- Human merge authority

Resealing an altered outer receipt is insufficient because the signed envelope and nested R16 receipt are independently revalidated.

## Preserved authority boundary

R17 never grants execution, deployment, trading or capital authority:

- `execution_authority=NONE`
- `can_execute=false`
- `deploy_permission=DENY`
- `can_trade=false`
- `capital_permission=DENY`

R17 contains no GitHub merge API, subprocess, network client, deployment code or private-key signer. Actual merge execution remains a separate operator-authorized integration step.
